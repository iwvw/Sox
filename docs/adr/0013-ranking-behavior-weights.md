# ADR-0013. 排序：行为加权落地（修订 ADR-0006）

日期：2026-09-29
状态：Accepted

## 背景

ADR-0006 定下的加权公式在实现里基本没落地：历史是**硬门槛**（只要命中历史，必然压过所有相关度更高的新结果），访问频次 `Count` 记录了但从不参与排序，无时间衰减、无负反馈、无上下文加成。

本 ADR 记录实际落地的排序规则，并明确与 ADR-0006 的差异。

## 决策

### 1. 相关度仍是主键，历史降为「同起点档内的加权项」

不采用 ADR-0006 的 `rel_match × 10000 + ...` 纯加权求和。原因：核心的 RankSortKey 是**字典序**打包（start > weight > tier），start 严格优先是为了避免「短名系统性占优」（Lertaro 实证：`wx` 会把 `iwxfe.mp` 排在 `wxfef.doc` 前）。改成加权求和会破坏这一点。

落地为**分层**：

```
1. start 档（RankSortKey 高 8 位）         ← 相关度主键，不同档直接决胜
2. 行为分（越大越前）
3. RankSortKey 完整字典序（weight/tier/span）
4. 路径长度 → 盘符 → 路径
```

即：**起点不同，相关度决胜；起点相同，行为分决定先后**。历史不再越权压过相关度更高的结果。

### 2. 行为分 = 频次 + 时间衰减 + 上下文加成 - 惩罚

- 频次：`log2(1 + count) × 300`
- 时间衰减：`<1h:+800 / <24h:+400 / <7d:+200 / 更早:0`
- 上下文加成：结果目录 == 当前上下文目录（对话框所在目录）时 `+500`，仅内嵌窗有上下文
- 惩罚：用户在结果列表中越过前 N 条选中第 N+1 条时，被越过的条目各 `+1`（上限 3），乘 `200` 从行为分扣除；被选中打开时清零

### 3. 行为数据存储

- 频次/时间：沿用 `search-history.json` 的 `StoredEntry(Count, Time)`，新增 `BuildBehaviorCache` 计算行为分（替换旧的「最近名次」`BuildPriorityCache`）
- 惩罚：单独存 `search-history-penalties.json`（path → 被越过次数），避免改动主 schema 造成迁移风险
- 打点：打开时 `Record`（频次+1、清该 path 惩罚）；打开前对该次结果列表中位于选中项之上的条目 `RecordPassover`

### 4. 排序无条件生效

`ApplySnapshot` 去掉「无历史命中就跳过排序」的短路，始终用比较器排序。行为分为空时，比较器退化为 RankSortKey 字典序，等价于核心顺序，无回归。

## 后果

- 从「历史硬闸」变为「相关度内微调」，符合「智能而非蛮横」
- 频次与时间衰减纳入，越用越准
- 惩罚与上下文加成落地（ADR-0006 遗留项）
- 行为数据与索引分离，重建索引不清历史
- 参数（300/800/400/200/500/200、上限 3）为初始值，需随使用反馈调参

## 关联

- 修订 ADR-0006（相关度硬门槛 + 行为加权），保留其「相关度为主、行为为辅」的意图，改为分层实现
- 相关代码：`SearchResult.cs`（比较器）、`SearchHistoryBucketSupport.cs`、`SearchHistoryStore.cs`、`HistoryRankWeights.cs`、`SearchViewModel.cs`
