# ADR-0009. 索引数据结构：Trie 改为线性扫描

日期：2026-09-29
状态：Accepted

## 背景

ADR-0002 原定用 Trie 前缀树做文件名前缀索引。实际落地后内存爆炸：200 万文件全盘扫描时进程占用 12GB 内存。

根因：Trie 每个节点实例化一个 `Dictionary<char, Node>`（.NET 空/单键 Dictionary 约 200B 开销）。200 万文件名平均 15 字符 ≈ 数千万节点，且文件名前缀共享极少（中文文件名几乎不共享前缀），节点数 ≈ 字符总数。三棵 Trie（lower_name + 拼音首字母 + 拼音全拼）叠加 → 10GB+。

## 决策

删除 Trie 与拼音 Trie，全部查询改为**线性扫描**：

- 主路径 `SearchByTerm`：一次遍历 `_entries`，合并命中 前缀匹配 / 子串匹配 / 首字母拼音前缀，收集到上限即停
- 全拼匹配 `SearchByPinyinFull`：仅在主路径候选不足 50 时补扫（全拼命中是低频场景）
- 拼音单字缓存（PinyinService）保留

性能依据：200 万条 lower_name 全量线性扫描只需 5-10ms，完全满足 PRD 的 <50ms 查询目标；正确性优先于微秒级优化。

## 后果

- 内存从 10GB+ 降至几百 MB（主表 + 路径表 + 字符串，未池化）
- 查询从微秒级降为 5-10ms，仍在验收线内
- 增量删除（USN）成本归零：直接从 `Dictionary` 移除，无需维护 Trie 节点
- 若未来需要微秒级查询：引入「排序数组 + 二分」方案（引用数组 ~16MB），作为索引缓存里程碑的优化项，不改变当前正确性
